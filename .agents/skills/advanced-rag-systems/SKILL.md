# Advanced RAG Systems Skill

## 1. Naive RAG Prohibition

Traditional, simple RAG pipelines (direct semantic query-to-vector matching returning raw text blocks) fail in regulatory environments due to lack of metadata structure, low semantic recall, and high noise. Naive RAG is strictly prohibited. The system must utilize structured, multi-stage context retrieval.

---

## 2. Structural Component Pipeline

To maintain high precision, the retrieval pipeline is organized into five specialized ingestion and extraction layers:

```
   ┌──────────────────────────────────────────────────────────┐
   │ 1. Contextual Ingestion & Hierarchy Chunking             │
   │    - Markdown header parsing                             │
   │    - Inject parent headers into chunk metadata            │
   └────────────────────────────┬─────────────────────────────┘
                                │
                                ▼
   ┌──────────────────────────────────────────────────────────┐
   │ 2. Multi-Query semantic Expansion (Groq LLM)             │
   │    - Expand user question into 3 search variants         │
   └────────────────────────────┬─────────────────────────────┘
                                │ Multiple Vector Queries
                                ▼
   ┌──────────────────────────────────────────────────────────┐
   │ 3. Metadata-Aware Retrieval & Vector Search              │
   │    - Filter search indexes by document/section categories│
   └────────────────────────────┬─────────────────────────────┘
                                │ Combined Raw Context Chunks
                                ▼
   ┌──────────────────────────────────────────────────────────┐
   │ 4. Contextual Compression & Similarity Pruning           │

```

## 3. Ingestion & Contextual Chunking Specifications

When reading regulatory PDFs or markdown manuals, parser scripts must store the hierarchical document state within ChromaDB's document metadata dictionary. **Never index raw, unstructured strings.**

### Required Metadata Key/Value Schema

Every stored chunk must include:
*   `source`: File basename of origin (e.g. `CPCB_EPR_Guidelines_2026.pdf`).
*   `section`: Heading structural block name (e.g. `Chapter III: Registration Requirements`).
*   `chunk_id`: Unique cryptographic hash representing the raw content.
*   `page`: Original page number where the block resides.

## 4. Multi-Query Semantic Expansion Pattern

Compliance questions are often formulated in casual vocabulary. The retriever should use the Groq LLM model (`meta-llama/llama-4-scout-17b-16e-instruct`) to generate semantic variants of the query, maximizing vector index hit-rates.

### Authorized Multi-Query Instruction Prompt

```
You are an advanced semantic query-reformulation engine.
Your task is to take a raw user question about plastic compliance and generate exactly 3 diverse, high-fidelity semantic variants of the question.
These variants will be executed against a vector search index to retrieve highly relevant regulatory chunks.

=== GUIDELINES ===
- Focus on synonym replacement (e.g., "variance" -> "deviation", "limit", "threshold").
- Maintain the original regulatory intent.
- Do not answer the question. Only output the variants.
- Output each variant on a new line, prefixed with "- ".

=== USER QUESTION ===
{question}
```

## 5. Metadata-Aware Vector Query & Relevancy Mathematics

ChromaDB matches vectors using **Cosine Similarity**. 

$$\text{Similarity}(A, B) = \frac{A \cdot B}{\|A\| \|B\|}$$

Where:
*   $A$ is the query vector generated by the embedding model (`nomic-embed-text`).
*   $B$ is the candidate document chunk vector.
*   The matching similarity score exists in the range $[-1, 1]$.

### Cosine Threshold Hard Boundary Rules

*   **Confidence Filtering**: Any chunk returning a similarity score **$< 0.45$** must be immediately discarded.
*   **Fallback Rejection**: If the maximum score across *all* retrieved chunks is less than $0.45$, the entire LLM generation node is bypassed, and the deterministic fallback response is returned directly.

---

## 6. Contextual Compression and Noise Reduction

Before context reaches the Groq generation context window, it must be cleaned and ordered logically:
1.  **Duplicate Pruning**: Identical chunk IDs returned by different query expansion variants are merged.
2.  **Structural Sort**: Chunks are sorted alphabetically by `source` and sequentially by `page`/`section` to represent a clean, continuous legal flow.
3.  **Noise Pruning**: System trims whitespace, footers, and redundant page markers from `chunk_text` properties to optimize token consumption.
